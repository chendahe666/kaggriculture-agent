# P4 最小物料与兑现诊断提案（未启动）

日期：2026-09-12。此文只依据官方引擎和已完成的 P1/P2 失败报告设计测量，不读取正在产生的 P3 标签，不实现策略或诊断运行器，不运行比赛。是否启动 P4 由主流程在 P3 完整证据出来后决定；下面的八场是上限，不是已批准执行或必须消耗的预算。

## 要回答的两个问题

1. **小麦为什么必须买？** 区分自产不足、自产尚未成熟、已收却未进入可取仓库、取麦路径或时间失配、仓容阻塞、订单槽位阻塞，以及买卖周转／原预售安排。不能用“买麦金额高”直接诊断采购浪费。
2. **甜瓜在哪里错过了兑现时点？** 分开观察可采、真正采收、到仓、成交；判断收入差来自生产成熟期、运输、仓中等待还是逐单位交易时点。相同总销量不足以确认某一种原因。

成功标准是得到**无残差的物料／现金账和可定位的时间链**，而不是发现更多失败动作、产生更高采收次数或在八场中证明策略提分。本轮没有干预臂，不报告反事实收益。

## 已知失败给出的约束

P1 netting 少花采购钱但同时减少卖麦收入，基本未增加收益；jit1 的平均采购下降约 1.3 万却增加缺麦喂养，分差下降。264 步满十个市场槽、265 步工人取粮的实例表明：工作先于市场，同步买入不能供本回合取粮。补足饲料又可能增加产出和溢出，feed-guard 也失败了。

P1 已发现市场后仓空仍可能在夜间因总携货超过仓容而丢麦。P2 则发现同样销量的早卖可能更差，额外收肥也可能替代更高价值生产。故新诊断不能假定“少买”“更多粮”“不逃跑”“更早到仓”“更早卖”中的任何一个独立最优。

## 最小记录集合

数据分三层。含任何私有仓库／携货／账本的原始事件只存本地 `inbox/diagnostics/material-p4/`，不提交 GitHub；公开报告仅放派生计数、恒等式残差和经过审查的例子。离线观测者可分别为两方建立其自身物料账，但对方账、未来事件、seed 和身份绝不进入本方线上特征或动作。日志不能成为代理的新输入。

| 层 | 必需字段 | 用途和边界 |
|---|---|---|
| 运行身份 | 候选／对手／引擎／记录器／配置 SHA，seed、seat、旧对照文件 SHA，真实 last-callable 入口，UTC、状态、错误、帧数、wall/CPU 范围 | 身份和标签仅作离线配对；逐行绑定具体字节 |
| 事件时序 | 单调 event_id、实际 action_step、day、phase、执行方、当日 actor_index、操作及参数、异常 | `(day, actor_index)` 是临时工槽位，不跨夜伪称同一个工人；同回合多个动作不能合并成一次 |
| 私有物料前后态 | WHEAT／MELON 的仓内数、每 actor 携带数，仓库所有商品总占用，种子 WHEAT／MELON 数 | 保存前态值副本，不能保留随后被引擎修改的同一 dict 引用 |
| 相关公开地块前后态 | 位置、kind/crop/animal、种植或放置日、yield_units、watered_today、fertilized_until_day、fed_today、cared_today、fertilizer_available、枯萎／逃跑状态 | 只对相关事件和状态变化记录；不能把 tile 潜在产量当成已经入手的商品 |
| 真实市场事件 | `_commit_unit` 返回值、op/item、传入的实际 price、现金／仓货／市场库存前后差、成交 event_id | 成功 BUY_PRODUCT 和 SELL 按单位记量；失败与未进入 commit 的请求另列 |
| 订单可用性 | 每回合请求市场队列、实际前十槽、被截掉的槽数；工作前现金、仓容、可取麦；必要时只读记录该回合 COK 原预售债和最终输出动作 | 检验采购时限、满槽与预售耦合，不重写订单或借贷账本 |
| 日界与结束 | 当日工作前，市场后，夜间自动返仓前后，重置完成后，最终 718 执行后的物料／现金快照 | 日终阶段不等价；最后一天没有新的夜间返仓 |

逐商品实际销售收入与单位采购支出仍记录全部九种商品，以检查“小麦或甜瓜改善”是否只是转移到其他商品的损失。详细生产和物流事件优先限定 WHEAT／MELON；FEED、夜间动物变化和相关 CARE/FERTILIZE 只作必要因果上下文。HIRE／BUY_LAND 成本单独记录，不能放进单位采购计数。

## Hook 位置与执行顺序

官方顺序为：工作动作 → `_process_market` → `_town_consume` → `_decay_plants` → 若到日界则 `_end_of_day`。定位时必须保留这个顺序，不以观测列表索引猜测“当天结束”。

| Hook | 官方位置 | 记录规则 |
|---|---|---|
| 真正被环境调用的 interpreter 外层 | `interpreter`，约 894 行 | 每回合开始从该次实际 state 建立 `id(farm)`／`id(private)` 到 seat 的映射，并设 action_step；finally 清理。**不能等市场阶段才建立映射**，因为工作先发生；也不能用两方恰好相同的状态值匹配身份。初始化后另建首回合映射。实现时验证包裹的是环境实际引用的 callable，不仅修改模块同名变量。 |
| `_apply_unit_action` 前后 | 312 行起；HARVEST 446 附近、FEED 505 附近 | 保存对应 actor 的位置、私有物料和当前地块前后态，原函数只调用一次；其返回 None 不是成功标志。通过真实状态增减生成物料事件，命令计数单独存。 |
| `_process_market` 与 `_commit_unit` | 544、652 行起 | 保存前十槽和前后仓容；commit 的真实布尔值和实际增减是单位成交依据。引擎先给双方报价再逐方提交，因此**不能拿第二方提交前的市场库存重新算其成交价**；用传入 price。缺少可验证槽位上下文时，槽位归属留空，不猜。 |
| `_do_hire`／`_do_buy_land` | 702、712 行起 | 现金下降并有对应手数／象限变化才记成功原子成本；失败申请单独计数。 |
| `_decay_plants`、`_daily_refresh_plants` | 752、769 行起 | 记录地块潜在产量衰减／枯萎；这是尚未采收的生产损失，不是仓库溢出，也不冲减已采收数量。 |
| `_daily_refresh_animals` | 805 行起 | 记录未喂养计数、逃跑和实际产量／care bonus 变化；用于判断缺粮的后果，不把“多活一天”预先当成利润。 |
| `_drop_inventories_to_shed` | 843 行起 | 逐商品记录自动入仓量和丢弃量。位置无关：夜间会自动处理所有人的携货。 |
| `_end_of_day` 前后 | 860 行起 | 只做日界审计、重置核对和公开商店变化；其中已经由子 hook 记过的返仓、损失和产量不得再次累计。 |

Nested hook 的阶段总量必须与独立的全局实际成交计数一致。代理配置由真实框架参数传递，不能沿用旧单参数包装而截断配置；观测、动作、RNG、引擎状态和原政策全局账本都不允许由记录器修改。异常继续传播并记录，不改成 PASS 或“成功空操作”。

### 失败动作绝不能计作真实采收

HARVEST 只有当相关携货的实际增加量为正，并与该地块产量减少或作物移除一致时，才生成 `harvest_units`。未成熟、空地、空产量、工人不存在等请求只记尝试及前后态。成功收 6 单位是一条事件、6 单位物料，不是“1 单位采收”；失败请求的真实产量是零。

FEED 只有 actor 的 WHEAT 实际减少 1，且动物 `fed_today` 从 false 变 true，才计一单位消耗。已经喂过、站错地块、没有该工人的请求不能统称“缺麦”。若动物有效且未喂，而该 actor 携麦为零，才标记携粮不足，并进一步分为：

- 全场 `仓＋携带` 都无麦：即时实物供给不足；
- 仓内有麦但该 actor 没麦：取粮／行动安排问题，不等于必须增购；
- 麦只在其他 actor 身上：分配或回仓时限问题，全场有货不等于该喂养动作可用。

PICKUP／PLACE 是转移，不是生产。有效 DROP 到仓可丢弃放不下的货；非仓边 DROP 不执行且不丢货。PLACE 满仓保留携货，不得按请求数量记交货。PLANT 消耗的是独立种子库，不消耗商品小麦。未进前十槽、解析无效或被忽略的订单，与 `_commit_unit` 返回 false 的订单分开；两者都没有成交量。

## 逐日守恒与零残差门

对每方、每天、商品 `k ∈ {WHEAT, MELON}`，定义 `S` 为仓内实物，`C` 为全部携货，`B=S+C`；所有 q 均取真实增减而不是命令请求量。

`B_end − B_start = buy_product + harvest − sold − consumed − discarded`

其中 WHEAT 的 consumed 是成功 FEED 单位数；MELON 的 buy_product 和 consumed 应为零，任何非零均作为模型／记录异常，而不是自动补平。普通搬运和自动返仓不改变 B，只有实际丢弃会减少 B。

分仓交叉式：

`S_end − S_start = buy_product + manual_deposit + auto_deposit − pickup − sold`

`C_end − C_start = harvest + pickup − manual_deposit − auto_deposit − consumed − manual_discard − auto_discard`

独立种子账：`seed_end − seed_start = successful_seed_buy_units − successful_PLANT_count`。不能把购入种子记为买入小麦商品，或把原材料全额采购金额解释为种植利润。

再加一条站立作物的辅助账：令 `U` 为尚在地块上的非负 yield_units 总和，WHEAT／MELON 均为非持续作物，则：

`U_end − U_start = new_plant_initial_yield + actual_WATER_bonus − harvested_units − decay_loss − destroyed_unharvested_yield`

后项包括 DIG 或缺水枯萎造成的剩余地块产量消失。初种 yield 及 WATER 增量直接从状态取，不按理论最大产量补数。日龄到了可采期但 U 没增加，是“资格变化”，不是商品突然入仓。

现金并行审计：`cash_end − cash_start = all_actual_sale_revenue − all_unit_purchase_spending − HIRE_cost − LAND_cost`。NPC 消费只改变市场库存，不直接给某玩家现金。单日、全局、分阶段与终态四类残差必须为零；任何不一致先停止经济解释，定位首个不一致事件。

日 0–28 的日末取实际自动返仓／重置之后；日 29 的日末取最后一个可执行动作 718 完成后，不能生成虚构的 719 动作或最后一次夜间回仓。夜间丢弃由 `_drop_inventories_to_shed` 唯一记账，不在父 hook 再算一次。

## 甜瓜：成熟 → 采收 → 入仓 → 成交

给每次成功种植分配离线地块代号 `(seat,x,y,plant_event_id)`。在每个真实动作前的当前公开状态判定它首次可采：仍是活的 MELON、日龄达到官方 first_yield_day=10 且 yield_units>0。记录 `first_ready_step`，不要根据未来仍存活或未来丰收倒填“本来可采”。

真实采收生成数量已知的携货批次；记录采收时刻、actor、手中已有货量。搬运记录真实到仓量及是手动还是自动。每次实际 SELL 记录单位数、price、市场库存时序、当时公开商店和仓容。由此计算：

- 可采到采收的等待；
- 采收到首次／全部入仓的等待；
- 仓内停留到真实出售的等待；
- 成交数量累计曲线、收入累计曲线、逐单位成交价和是否地板价。

引擎商品可混同，没有原生“第几块田的这一单位被卖出”标签。若追踪跨批次转移，FIFO 仅是预先固定的可复现会计约定，必须标注为约定；不能把它当成真实物流身份。主要结论以可直接观测的累计采收／入仓／销售曲线及总量守恒为准。到终局仍未采、未入仓或未售的批次右删失，时间留空并记录所处阶段，不能写成等待零。

还需区分“计划提前交货”与“计划提前成交”：非终日即使没有主动运输，夜间也可能自动入仓；这时主动运输的价值是提前获得日内出售或取用机会，而不是凭空避免所有携带残留。P2 已证明这种提前机会未必值更多钱。

## 最多八场的分阶段预算

不新挑保留 seed，不依据 P3 新标签调整样本。本提案固定复用已观察的 COK 对 Arlene 场景，候选仍为原 COK；每场同时记录双方各自物料账，代理之间不共享这些账。Arlene 源文件仅本地评估，不复制动作带。

| 批次 | 场景 | 新增整局上限 | 推进条件 |
|---|---|---:|---|
| A | seed 91101／seat 0；91103／seat 0 | 2 | 主流程先授权；记录器身份、短机制测试和来源冻结完成 |

| C | seed 91102、91104，各双座位 | 4 | 尚有明确需要跨已知场景否证的来源／时点问题；不因“预算还没用完”而启动 |

所有失败运行、调试重跑也计入这八次上限；不是失败后再补八场。纯合成事件／最多四帧官方微测试单独记数，不伪称完整联赛。开始记录前先验证：成功／失败 HARVEST、欠粮与已喂 FEED、满仓 DROP 与 PLACE、日终溢出、买卖同回合锁步价格、订单截断、真实配置透传，以及最后一天无夜间返仓。

冻结后每场都与相应既有原版控制比较最终现金、实际销售数量／收入、单位采购及商店路径；日志包装不得改变结果。若不一致，该场只算记录器回归排查，不作为策略原因证据。只开旧开发资料；912001–912090 继续封存，没有正式确认，也没有学习模型训练。

## 与 P1 的关键区别和退出条件

P1 在“不完全表示物料可用时点”的条件下直接改采购、补粮或提前配送；本提案首先**不改任何动作**，补齐实际采购单位、已采物料、 actor 可取性、夜间损失、市场槽位与兑现时点。只有这条因果链成立，之后才另立有界干预方案；不会把本次数据写成“已经证明某个补丁能多赚”。

若高采购主要对应有用喂养／价差周转，而替代自生产无法在取粮前可达，就否定“可轻易减少采购”的解释。若甜瓜差异主要来自更早成熟，而采收到售出的等待已短，就不继续优化最后一段配送。若增产主要落在地板价或挤占其他商品，就不把最大产量作为目标。若两场已足以排除某条解释，停止该支线；若八场仍不能识别原因，报告不可识别项，不继续无上限追踪或开启 P4 策略搜索。
